# Documentos y reportes

Propietario independiente BE-19/BE-20, versión 0.4.1, puerto 5112 (6112 por Compose local). API, worker e imagen propios. Datos: vistas de `stored_file`, `document_metadata`, `file_scans`, `export_jobs`; colas técnicas filtradas. No necesita MongoDB.

Los sujetos se autorizan mediante su propietario y JWT delegado. El proveedor local o GCS almacena objetos privados; generación, SHA-256 y análisis ClamAV limpio son requisitos de descarga. El worker crea PDF/CSV/XLSX con nombres deterministas y recuperación idempotente.

Contratos JSON/XML/XSD en `contracts/`; configuración, decisiones y migración 013 en [documentación correctiva](../../../documentation/entrega-final/backend/correccion/Arquitectura_y_decisiones.md). Las rutas v1 documentales de Transporte delegan una sola vez al nuevo propietario.

Instalación: dependencias `requirements-storage.txt`, configuración propia con SQL/Redis/JWT/clave de servicio, proveedor privado local o GCS y ClamAV. `run.py documentos --config RUTA` y `worker.py documentos --config RUTA` ejecutan procesos separados. `Dockerfile` empaqueta este dominio y utilidades técnicas. `/health/storage` comprueba el proveedor activo; la ausencia de motor nunca se interpreta como análisis limpio.

### Almacenamiento privado local o GCS

`STORAGE_PROVIDER` selecciona `local` o `gcs`; si se omite, se conserva GCS cuando existe `GCS_BUCKET` y se selecciona local en otro caso. Cada archivo conserva su proveedor inmutable. La migración compartida 019 marca las filas anteriores como GCS; no copia ni altera objetos. Mantenga la configuración GCS mientras existan archivos históricos que deban consultarse. No cambie de proveedor esperando que los objetos se migren.

Para local configure `STORAGE_LOCAL_ROOT` como directorio absoluto privado, persistente, sin enlace simbólico y accesible al usuario del proceso; configure `STORAGE_PUBLIC_BASE_URL` como origen HTTPS externo exacto, sin ruta, consulta ni credenciales. Comparta el mismo directorio y la configuración/clave privada de Documentos entre su API, worker y módulo web. Compose monta `private-files` en `/var/lib/redhouse-private` y prepara su propiedad para UID 10001. El volumen debe incluirse en respaldos y recuperación; sustituirlo por un directorio vacío no recupera objetos. No se sirve el directorio directamente.

Prepare, verifique y descargue mediante las API existentes. La respuesta de preparación devuelve `upload_url` y `upload_headers`; el cliente debe transmitir exactamente esas cabeceras. Las URL locales incluyen capacidades cifradas con vencimiento de cinco minutos y revalidan JWT, Redis, rol y acceso al recurso en cada transferencia. No registre URL completas ni capacidades en Nginx, proxies, clientes o telemetría. La carga local limita el cuerpo a 10 MiB, comprueba tamaño y SHA-256, y no sobrescribe un objeto. La descarga exige generación verificada y análisis limpio; vuelve a comprobar el hash. La verificación sigue usando ClamAV real configurado y falla cerrada si no responde. Los metadatos API mantienen el límite de 262144 bytes. El proxy debe enrutar `/storage/v1/objects/` al portal, limitar ese cuerpo a 10 MiB y no registrar la URL; debe conservar 256 KiB para las demás rutas de API.

`/health/storage` informa el proveedor activo. La salud local comprueba directorio privado, espacio libre mínimo de 10 MiB y escritura con sincronización; no demuestra disponibilidad futura, cuota, integridad de respaldos ni funcionalidad GCS histórica. Exportaciones locales mayores de 10 MiB fallan y requieren un diseño específico de streaming antes de admitirlas. GCS sigue usando sus URLs firmadas y configuración propia.

Una instalación nueva (`install.sh` o el bootstrap de Compose) ya deja `STORAGE_LOCAL_ROOT` (`.local/runtime/private-files` con modo 0700, o `/var/lib/redhouse-private` en Compose); sin `GCS_BUCKET` el proveedor implícito es el local, por lo que `/health/ready` responde 200 desde el primer arranque. Lo único que no se configura solo es `STORAGE_PUBLIC_BASE_URL`: los enlaces temporales de subida y descarga exigen un origen HTTPS, y el portal local escucha en HTTP, así que esas operaciones responden 503 `storage_unconfigured` hasta que se configure con el comando siguiente.

Para una instalación local existente, prepare una copia de seguridad de su JSON privado y ejecute explícitamente `python3 deployment/configure_local_storage.py --config /ruta/privada/documentos.json --directory /ruta/absoluta/privada/archivos --origin https://origen-configurado`. El directorio debe pertenecer al usuario de los procesos y no permitir acceso de grupo ni otros. Reinicie el módulo web, la API de Documentos y el worker para cargar la configuración. El comando conserva los campos GCS; cambiar el proveedor no modifica ni migra sus objetos. Para Compose, configure el JSON con `STORAGE_LOCAL_ROOT=/var/lib/redhouse-private` y el origen HTTPS público, ya que el directorio del volumen pertenece al UID del contenedor. La herramienta de host no prepara ese volumen.

Si el proceso cae entre la creación del enlace final y la eliminación de su nombre temporal, el archivo final conserva su contenido; puede quedar un nombre oculto temporal adicional. Debe inspeccionarse y limpiarse con un procedimiento administrativo que identifique el mismo inodo y preserve el nombre UUID final. No borre indiscriminadamente archivos del volumen.

Contrato binario local v1: `PUT /storage/v1/objects/{capacidad}` recibe el cuerpo exacto y `Content-Type` indicados al preparar; requiere `Content-Length`, acepta como máximo 10485760 bytes y responde `201` al guardar o `412` si el objeto ya existe. Tras un `412`, el cliente debe consultar/verificar la operación preparada, sin sobrescribirla. `GET` de esa misma ruta con capacidad de lectura distinta devuelve el contenido verificado como descarga. La capacidad cifra el JWT de la operación y solo sirve para el método y generación indicados durante cinco minutos; la autorización vigente se comprueba nuevamente en cada acceso. Las respuestas pueden incluir `401` por sesión/capacidad inválida, `403` por acceso, `409` por estado o integridad, `411` por longitud ausente en el gateway, `413` por límite, `422` por MIME/tamaño/hash y `503` por dependencia. La preparación/verificación y solicitud de descarga conservan sus formatos JSON/XML existentes. El cuerpo binario no es JSON ni XML.
