# Propuesta: reautenticación ligada a una operación y de un uso

Estado: **implementación en worktree aislado, pendiente de regresión y revisión**. No modifica el backend ni los contratos desplegados. El mecanismo desplegado no cumple el requisito de comprobante de un uso ligado a los datos: `redhouse/reauth.py` lee el valor con Redis `GET`, y `strong_auth.reauthenticate` lo liga a usuario, sesión, institución, versión de permisos, operación y recurso, pero no al contenido ni a la clave de idempotencia. El decorator lo comprueba antes de `atomic`. Un mismo comprobante válido puede autorizar varios cuerpos o claves para el mismo ámbito durante su vigencia.

## Restricciones del diseño

- Un usuario debe confirmar la operación exacta y la versión de datos mostrada. El mismo comprobante no puede iniciar otra intención, incluso con peticiones simultáneas a réplicas distintas.
- Un resultado confirmado debe poder recuperarse con la misma clave y cuerpo sin volver a ejecutar el efecto. El servidor revalida identidad, sesión, permisos y acceso al recurso antes de entregar el resultado; no usa esa recuperación para autorizar una nueva escritura.
- JSON y XML deben representar la misma intención si, tras las validaciones y valores por defecto del propietario, producen el mismo DTO. No firmar bytes XML arbitrarios ni exigir a cada cliente reproducir detalles internos de Pydantic. Los cuerpos distintos, versiones distintas, cambios de ruta, operación, tenant, actor o clave no son intercambiables.
- No trasladar contraseñas, OTP, comprobantes ni cuerpos clínicos a logs, auditoría genérica o almacenamiento durable del cliente. El diario puede guardar cifrados únicamente la intención y clave necesarias, con la política existente. No incluir datos clínicos en el reto para Identidad.

## Protocolo propuesto

1. El cliente construye y conserva primero la intención y una clave de idempotencia nueva, antes de presentar el desafío. La clave y el cuerpo se mantienen estables hasta recuperar resultado o resolver el intento; cancelar antes del envío deja el intento cancelado sin operación de negocio.
2. El cliente envía al propietario la operación preparada sin comprobante. Tras autenticar, comprobar rol, validar el DTO y autorizar explícitamente el recurso sin mutarlo, el propietario responde `reauthentication_required` con un reto firmado. Alternativamente podría existir una ruta de preparación dedicada; el 403 evita duplicarla, pero necesita un contrato de error versionado y consumidores conscientes. El reto liga actor, tenant, sesión, versión de permisos, servicio, operación, método/ruta/recurso, clave, huella del DTO normalizado, versión de esquema/canonización, nonce y vencimiento; no contiene el cuerpo clínico. No se puede firmar antes de comprobar el recurso: hoy muchas autorizaciones `own` ocurren dentro del controlador, después del decorator. Separación criptográfica de propósitos, llaves entre servicios y rotación requieren revisión.
3. Identidad valida firma, emisor, operación permitida, vigencia y coincidencia con JWT/sesión/tenant/versión actuales; realiza contraseña y factor requerido. Emite un comprobante aleatorio breve ligado al descriptor. Redis conserva solo su hash y ámbito mínimo con TTL; la contraseña y OTP permanecen solo en memoria. Un reto de otro servicio/ámbito no puede utilizarse para obtener o consumir una prueba válida.
4. El cliente envía la operación con la misma clave, cuerpo y comprobante. El propietario vuelve a validar JWT/Redis, autorización y estado actual, normaliza el DTO con la misma versión y verifica alcance/huella del comprobante. La verificación de una prueba ajena o un cuerpo distinto no debe destruir la prueba legítima ni causar escrituras.

El intercambio revisado usa `POST /api/v1/auth/reauthentication-proofs`, con `challenge`, `password` y `otp` opcional; conserva el DTO y XSD `reauthenticate`. La antigua ruta `/api/v1/auth/reauthenticate` responde 410 `reauthentication_protocol_obsolete` y no emite comprobantes. El cambio requiere coordinar Identidad, propietarios de las operaciones, web y escritorio; clientes antiguos fallan de forma explícita y móvil no consume estas operaciones. Activar la revisión solo cuando estén desplegados los clientes compatibles y se haya completado la regresión. No aceptar pruebas antiguas ni utilizar la versión general 0.4.4 como señal del protocolo.
5. Preferir el ledger idempotente existente en lugar de introducir otra tabla: la prueba queda ligada a **una sola intención y una sola clave**, y el bloqueo/UNIQUE de `atomic` hace que esa clave y huella produzcan como máximo un efecto SQL. Dos claves o cuerpos distintos no coinciden con el ámbito firmado. Si la transacción revierte, el mismo intento puede reanudarse con la misma prueba aún válida o una nueva ligada al mismo cuerpo/clave; no queda consumo falso. La semántica es «un comando, con replay idempotente», no «el token solo puede presentarse una vez»: si la norma exige literalmente esto último, se necesita una decisión distinta y probablemente estado durable adicional. No guardar token en claro.
6. Si el efecto ya quedó confirmado con igual actor/sesión/ámbito, clave y huella, se devuelve el resultado durable sin repetir la mutación; el reenvío no consume ni habilita otra intención. Si se perdió la respuesta antes del commit, el cliente consulta el recibo autorizado y, si no existe, puede obtener una prueba nueva para la **misma** intención. Con una sesión nueva o cambio de permisos se debe exigir la autorización definida para esa recuperación, no reutilizar la prueba antigua. Una huella distinta con la misma clave es 409.

La recuperación no debe depender de que Redis recuerde un comprobante una vez confirmado el efecto: autenticar sí requiere Redis, pero la identidad y resultado del comando deben ser durables en SQL. Si Redis está caído, no se crean nuevas autorizaciones ni se atienden peticiones protegidas. Una lectura Redis seguida de `GETDEL` y luego escritura SQL no ofrece atomicidad: una caída en medio puede quemar la prueba sin efecto; permitir reaprovecharla sin recibo durable puede duplicar. El reto firmado y el ledger existente deben revisarse contra el modelo real de credenciales y privilegios, no asumirse terminados por este diseño. Las filas actuales de `service_idempotency` contienen servicio, usuario, clave, operación, huella y resultado, pero no sesión ni tenant; recuperar tras cambio de sesión/tenant exige una política explícita y podría requerir columnas aditivas en ese mismo ledger. No reinterpretar ni sobrescribir huellas históricas.

## Reserva y revocación concurrente

`reservation_create` utiliza la saga `operations`, no `atomic`. La creación inicial de la operación con su clave/huella debe quedar durable **antes del primer efecto remoto**, y solo tras validar el comprobante ligado a esa misma intención. Las etapas posteriores, consultas por clave, reanudación y compensación deben recuperar esa operación autorizada, sin crear otra ni utilizar un comprobante para cambiar su contenido. Un fallo previo al commit no consume la prueba; un fallo posterior deja una operación consultable y recuperable con sus estados reales. Definir la facultad de reanudar por usuario o worker y comprobar que `operation_resume` no altera la intención.

La comprobación Redis actual y una transacción PostgreSQL no son una operación distribuida atómica. Para garantizar que una revocación ya completada prevalezca, proponer un punto de linealización durable: el cambio/revocación de sesión y de permisos debe coordinar una fila/versión SQL bloqueada también por la mutación crítica, sin relajar la validación Redis obligatoria. Deben revisarse todos los caminos, incluidos reutilización de refresh, logout, cambio de rol, baja y recuperación de cuenta; hoy algunos invalidan Redis antes de actualizar SQL. Establecer un único orden de bloqueos para evitar deadlocks y no afirmar revocación instantánea o semántica linealizable antes de probarlo. Definir qué ocurre si Redis deja de estar disponible entre su comprobación y el commit; un segundo chequeo aislado reduce una ventana, pero no hace atómicos ambos almacenes.

## Clientes y transición

La web ya genera `command_key` antes de solicitar prueba, pero solo envía operación/recurso/credenciales; debe solicitar el reto con el DTO y la clave que realmente enviará. Un 403 `reauthentication_required` debe transportar el reto mediante un contrato JSON/XML versionado y no marcar el diario como fallo definitivo. El cliente escritorio actual convierte 403 genéricos en FAILED/CONFLICT y debe tratar este código antes de esa rama. Mantener su consulta por clave de reserva y manejo de respuesta perdida. Escritorio conserva las credenciales en memoria y usa diario cifrado; hoy algunos dictámenes generan/persisten clave después de reautenticar, por lo que deben cambiar a `PREPARED` antes del reto y conservar cuerpo/clave para recuperación. El móvil no llama actualmente a reautenticación ni envía el encabezado; si se habilita una operación que la exija necesita flujo/contrato explícito y debe conservar el diario existente, sin guardar contraseña u OTP. La renovación de JWT actual conserva `sid`; una nueva sesión o versión de permisos invalida el alcance anterior.

Publicar primero la capacidad versionada y pruebas de interoperabilidad; actualizar contratos JSON/XML/XSD y todos los clientes que ejecutan operaciones protegidas. Una fase compatible con el mecanismo anterior **sigue siendo vulnerable** y no debe declararse resuelta. El corte debe deshabilitar explícitamente las pruebas antiguas, impedir fallback silencioso y tratar los retos pendientes de forma segura. No cambiar el alcance clínico ni la configuración productiva antes de la aprobación e integración correspondientes.

## Pruebas preparadas y matriz de aceptación

`apps/services/tests/test_reauthentication_single_use.py` cubre el intercambio nuevo. Una suite anterior aprobó 18 casos en 312,92 segundos con PostgreSQL, Redis y MongoDB aislados y TOTP real; esa ejecución precedió al cambio de ruta. La suite posterior registró 37 aprobados y dos fallos en transición de regla. Tras corregir el bloqueo sobre el perfil inmutable, ambos casos dirigidos aprobaron; corresponden a ejecuciones distintas. Los hashes coincidieron antes y después de cada ejecución. El primer intento quedó bloqueado por el sandbox al abrir sockets; la ejecución real posterior requirió autorización acotada para los sockets locales. Los JUnit, hashes, incidencias y límites constan en `documentation/evidencias/entrega-final/reauth-20261113/RESULTADOS.md`.

La aceptación debe incluir, en JSON y XML y al menos dos réplicas:

- Igual DTO con distinto formato/orden y valores por defecto equivalentes; cambio de decisión, versión, motivo, recurso, ruta, servicio, clave o tenant; vectores de canonización estables y errores de validación sin consumo.
- Prueba ajena, vencida, manipulada, emitida para otra sesión, revocación, cambio de rol, logout y renovación de JWT; ningún intento inválido destruye una prueba correcta de otro ámbito.
- Carrera de una prueba con claves distintas, con cuerpo igual o distinto: como máximo un efecto; misma clave/cuerpo simultáneos: un efecto y resultado coherente. Confirmar eventos y recibos, no solo HTTP.
- Corte antes de crear el recibo/commit, tras insertar y antes del commit, tras commit y antes de respuesta, Redis inaccesible, PostgreSQL inaccesible, caídas/reinicio y repetición desde otro proceso. Reanudar la saga en cada punto sin duplicar reserva, cupo, efecto ni auditoría.
- Revocación/rol en carrera con el commit, orden de bloqueos y ausencia de deadlocks; documentar el punto exacto a partir del cual se considera completada la revocación y los límites observados.
- Flujo web, escritorio y móvil aplicable con diarios durables, expiración del reto, cancelación, cambio de cuenta, credenciales eliminadas y recuperación. No contar compilación o simulación como prueba física.

El ledger debe conservar cada identidad de comando al menos mientras cualquier prueba asociada pueda ser válida. Si se restaura una copia SQL anterior, invalidar las sesiones y pruebas previas o rotar una época durable antes de admitir escrituras: de otro modo Redis podría conservar una prueba mientras el recibo desapareció. La idempotencia local no convierte en atómicas las llamadas remotas; cada efecto externo de una operación protegida requiere su propia clave o compensación verificable. El inventario usa huellas distintas en `atomic` y `reserve`: la canonización nueva debe versionarse sin romper la búsqueda ni reinterpretar registros históricos.

El provisionamiento nuevo revoca DELETE de `access_inventario.operations` a `rh_inventario`. En instalaciones existentes, ejecutar como propietario o rol autorizado `apps/services/scripts/reauth_operations_retention.sql`; es idempotente y conserva SELECT, INSERT y UPDATE usados por la saga. Las operaciones y recibos se conservan indefinidamente por ahora. Una futura limpieza requiere política documentada, retención mayor que el TTL de cualquier prueba, operaciones terminadas y protección frente a restauraciones anteriores; todavía no existe ni debe suponerse implementada. La suite comprobó el privilegio efectivo bajo el rol de Inventario y la repetición de reserva 202 en JSON y XML; no demuestra recuperación en todos los puntos de interrupción de la saga.

La autorización y Redis se comprueban al recibir la petición y otra vez tras adquirir el bloqueo de idempotencia. Una revocación que ocurre después de esta última comprobación puede coincidir con un commit ya en curso: Redis y PostgreSQL no tienen una transacción conjunta. Las evaluaciones y los perfiles de laboratorio son inmutables; no se utiliza SELECT FOR UPDATE sobre sus vistas de acceso. La transición de perfil adquiere el advisory lock `profile:<id>`, comprueba la secuencia y añade una acción inmutable con unicidad por perfil y secuencia. La vigencia de dependencias remotas se vuelve a consultar, pero no se presenta como una transacción distribuida.
