# Integración de la web

El portal permite backend modular autónomo (`monolith`) o consumo HTTP explícito (`microservices`): [operación, arquitectura y presentación](../../apps/web/README.md). Los servicios siguen ejecutándose sin depender de plantillas, sesiones internas ni conexiones de la web.

Se incorporaron contratos de consulta para indicadores autorizados, usuarios minimizados, detalle de recursos y procesamiento, historial de evaluaciones, rankings, propuestas y reservas. Cada contrato consulta únicamente las vistas autorizadas de su propietario en la base compartida. Los filtros documentados se parametrizan, limitan búsqueda y validan enums/UUID; el total refleja el conjunto filtrado. Las proyecciones regionales de coordinación omiten identidad clínica. Los indicadores de solicitudes del coordinador son institucionales: no se reconstruyen relaciones mediante SQL contra otros servicios.

La web consume disponibilidad regional con caché Redis y revisa las operaciones pendientes antes de planificar. API v1, JWT, versiones, idempotencia, JSON/XML y seguridad de las llamadas internas mantienen los contratos anteriores. Los DTO nuevos se incluyen en OpenAPI y en los esquemas equivalentes de salida. En modo modular, el backend web ejecuta los mismos módulos con sus credenciales SQL/Redis limitadas y sus workers propios. No requiere listeners de las API ni cambia de backend tras un fallo. En modo HTTP, las API conservan esos accesos. No existe doble escritura al monolito antiguo.

`scripts/seed_nuevo_leon.py` provisiona seis instituciones y carga registros ficticios por API, con perfiles diferenciados. Su SQL se limita al provisionamiento explícito de identidades en un entorno nuevo; no lee ni modifica la base del monolito retirado. Restablecer límites con `restore` y reiniciar después de una carga. `scripts/integrated.py` gestiona web y entorno propio conjuntamente; `scripts/local.py` continúa disponible para operar solo servicios.

La vista de archivos de cada traslado permite carga validada, consulta de estado, verificación y descarga privada GCS. La autorización deriva del traslado y del perfil; el navegador no recibe credenciales de nube. Las pruebas de continuidad ejecutan sangre, órganos y donación/procesamiento con todas las API detenidas; consultar resultados actuales en el expediente del segundo parcial.

La sesión técnica del portal usa Redis con TTL, cifrado y ACL exclusivos; PostgreSQL conserva cierres y revocaciones pendientes. La tabla `web_runtime.session_revocations` no contiene expedientes clínicos ni concede permisos del dominio. Véase [actualización y recuperación](Instalacion_y_operacion.md#actualización-de-sesiones-del-portal-20-de-octubre).
