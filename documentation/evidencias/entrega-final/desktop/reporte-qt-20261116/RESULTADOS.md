# Reporte Qt/XML con almacenamiento local

El 16/11/2026, `operator1` solicitó desde Qt un reporte sintético de inventario en CSV. El cliente consultó el listado y el detalle, y descargó 1.698 bytes por HTTPS. La verificación confirmó archivo VERIFIED, análisis CLEAN y SHA-256 coincidente. El proceso terminó con salida 0 y la familia de sesión propia quedó cerrada en SQL y Redis. El [recibo saneado](receipt-saneado.json) omite identificadores de sesión, credenciales y contenido del reporte.

El fixture LOCAL usó ClamAV real y ámbito ACADEMIC. Antes del alta se comprobó que no hubiera trabajos PENDING; después se exigió que el único pendiente fuera el recién creado. El arnés invocó una vez `process(limit=1)` del propietario, sin un worker continuo de reportes. La selección del archivo de destino se automatizó mediante un doble de diálogo; la solicitud, consulta y descarga emplearon la aplicación Qt y el servicio XML reales. Los oráculos SQL y Redis pertenecen al arnés, no al cliente de escritorio.

Las capturas muestran [solicitud](01-solicitud.png), [listado](02-listado.png), [detalle](03-detalle.png) y [descarga](04-descarga.png). Dirección inspeccionó solicitud y descarga; también se revisaron listado y detalle. El reintento RETRYABLE se comprobó por separado [con dobles](../iteracion-reintento-reportes/RESULTADOS.md); este recorrido no lo ejerció. Tampoco acredita descarga GCS real desde escritorio, otros formatos, Windows ni uso clínico.

Los diarios, recibos con IDs, archivo CSV y configuración permanecen privados. No repetir el alta sobre la base conservada para reconstruir evidencia.
