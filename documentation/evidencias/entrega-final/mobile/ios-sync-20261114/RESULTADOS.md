# Observaciones iOS: recuperación tras terminar el proceso — 14/11/2026

## Resultado y alcance

En iPhone 16 Pro, **Red House Lab recuperó una observación sin confirmación después de terminar su proceso con SIGKILL**. Conservó la identidad del comando y obtuvo su resultado mediante GET, sin otro POST ni otra escritura. El usuario confirmó «Sin confirmación» antes y después del reinicio, y finalmente ambas observaciones como «Registrado». Los oráculos independientes comprobaron actor, dispositivo, ID/fingerprint, una fila y un evento coincidente SQL/Mongo para el comando del ensayo. Un transportista ajeno recibió 403. La tarea permaneció PREPARED, versión 2 y secuencia 2, con su única transición histórica.

Es recuperación en primer plano sobre el fixture sintético conservado, no prueba de ejecución programada de BGAppRefresh, de un corte físico de red ni de cambio de cuenta desde la interfaz. El 503 se inyectó después de persistir el primer POST exitoso; el backend siguió disponible para las demás operaciones. No se realizaron nuevas transferencias de custodia, pruebas clínicas, QR, fotografías ni GPS como criterio de aceptación de este recorrido.

## Casos conservados

1. **Descubribilidad: ensayo no iniciado.** El acceso anterior para crear una observación estaba oculto en el formulario de transferencia y exigía atravesar QR/sello. El usuario abrió el bloque de sincronización, que solo ofrecía consultar resultados. La captura diagnóstica real mostró «Observaciones por sincronizar (0)»; dirección la inspeccionó. SQL confirmó cero comandos. [Registro](01-descubribilidad.json). No se atribuye un fallo de sincronización a ese intento.
2. **Sincronización positiva sin inyección.** Después de incorporar el acceso directo, una primera nota quedó RECORDED: actor transport1, una fila y un evento SQL/Mongo coincidente. [Oráculo](02-sin-inyeccion.json). Su texto no coincidió con el marcador exacto del arnés inicial; no se sustituyó la respuesta por 503 ni se probó reinicio. El [oráculo dirigido](intento-marcador-inactivo.json) rechazó esa precondición. El contador de la interfaz incluía también filas RECORDED; su número no demostraba estar pendiente.
3. **Recuperación con inyección y reinicio.** Se conservó el caso anterior y se reanudó el mismo fixture, sin repoblarlo. Baseline: un comando. El arnés pasó a interceptar el primer POST201 de TRANSPORT_OBSERVATION para la tarea conservada, independiente del texto de la nota y manteniendo autorización backend e identidad/cuerpo estrictos. Una nota nueva produjo el POST201 persistido; el arnés entregó un 503 con contrato Error válido y bloqueó GET y replay POST hasta liberar explícitamente el resultado. [Oráculo previo al reinicio](03-antes-reinicio.json).

Solo después del oráculo aprobado y de la confirmación humana de «Sin confirmación», se terminó exclusivamente el PID de Lab con SIGKILL y se reabrió el mismo bundle. No se reinstaló, borró almacenamiento ni introdujeron credenciales. Llegaron consultas del mismo command_id mientras el resultado permanecía bloqueado; el usuario volvió a confirmar la etiqueta sin confirmación. Tras liberar el resultado llegaron dos GET antes de ejecutar cualquier cliente HTTP independiente. El [oráculo de ese punto](04-antes-negativo.json) confirmó un solo POST delegado, una fila y un evento para el nuevo comando. La tabla contiene dos comandos en total: el positivo previo y el nuevo del ensayo.

El [control ajeno](05-negativo-ajeno.json) autenticó otra cuenta sintética transport2, recibió 403 con contrato Error válido y cerró exclusivamente esa sesión nueva: familia revocada en SQL y ausente en Redis. No equivale a cambiar la cuenta del teléfono. El [oráculo final](07-oraculo-final.json) confirmó que ese control no añadió otra observación ni alteró la tarea. El usuario confirmó al final «ambas dicen Registrado». [Confirmación y cierre](06-confirmacion-y-cierre.json).

## Interfaz, artefacto y límites de inspección

El acceso directo «Añadir observación» abre un diálogo independiente del formulario de transferencia. Ambos accesos reutilizan una sola llamada a ObservationQueue.enqueue con identidad, dispositivo y versión existentes; no ejecutan custodia. El texto se recorta con trim y admite 6–1000 caracteres. Un fallo conserva el borrador; solo un guardado local exitoso lo limpia.

El artefacto físico del recorrido fue **iOS Lab Debug, ejecutable SHA-256 `46af5bead645b424e2f292140413120736083938e5875207daed5ab92dd148f4`**, anterior al ajuste posterior del contador. [Manifiesto de identidad/firma](artefacto-lab-del-recorrido.json): bundle `org.redhouse.mobile.lab`, origen de laboratorio exacto y CA fijada; perfil hasta 21/11/2026 18:32:33 UTC. La actualización se instaló sin desinstalar. Tras reanudar el backend, una lectura autenticada de Identidad confirmó transport1, sin leer secretos del Keychain.

El runner de captura inicial fotografió su propia pantalla negra; no prueba una pantalla negra del producto. Una captura diagnóstica posterior, activando Lab existente una sola vez y comprobando el mismo PID, mostró el bloque antiguo y sus cero observaciones. Para el diálogo nuevo se intentó una sola captura coordinada: el runner no pudo inicializar UI testing por `LocalAuthentication Code=-4`, «Authentication canceled». El PID de Lab permaneció igual. [Límite registrado](limite-captura.json). El usuario confirmó ver el diálogo y sus estados, pero **no se declara inspección visual de dirección ni captura válida del diálogo nuevo o de la recuperación**. No se encadenaron más intentos XCTest ni se escribió texto o credenciales desde ellos. Las capturas físicas y notas originales permanecen privadas.

Después del recorrido se corrigió el contador para distinguir pendientes PENDING/SENDING/UNCERTAIN, enviadas RECORDED y otros resultados para revisar. Su fuente no cambia la cola ni las reglas backend. Ese contador no estaba incluido en el ejecutable físico 46af5be; el [recibo final de compilación e instalación](PAQUETES.md) identifica los binarios posteriores, sin presentarlos como repetición de este flujo.

## Entorno, fuentes y cierre

Se reutilizaron las bases, cuentas, dispositivo, tarea, TLS y lab.json del fixture conservado; nunca se ejecutó init/provision ni se sobrescribió lab.json. Las comprobaciones del arnés con un doble WSGI validaron el envelope503 contra el esquema Error real, el bloqueo de GET/tres replay POST sin delegarlos, rechazo de ID/cuerpo alterados y liberación explícita. No son pruebas físicas ni nuevas pruebas del backend productivo.

[Control de fuentes](fuentes-backend.json): 140 archivos de producto/arranque permanecieron idénticos durante el ensayo; el test de portal ajeno no pertenece a ese conjunto ni fue importado por el runner. Los [hashes de los scripts usados](harness-fuentes.sha256) permiten cotejar los originales privados conservados en `.local/artifacts/mobile/ios-sync-prepared-20261114/`. No se publican contraseñas, tokens, claves, notas ni Keychain. El hash de lab.json permanece `166fa8c0a547d45c4ed57407477eb13a8f0d423c077975d8fefdc21e7e041f6d`.

El fixture terminó con código 0; app Lab, sesión y datos se conservaron. La app normal y su Keychain no participaron en el ensayo. Los permisos nativos negativos, accesibilidad, TLS negativo y BGAppRefresh real siguen pendientes; no se cierra integralmente la etapa 04.
